# Gymnasium Env Patterns

Applies to everything under `wargame_rl/wargame/envs/`.

## Structure

- `WargameEnv` extends `gymnasium.Env`; typed obs/action/info/config (all Pydantic)
- Config: `WargameEnvConfig` (pydantic-yaml) from `configs/`
- Actions: polar (angle, speed) pairs per model via `ActionHandler(config, n_models=..., n_shoot_targets=...)`; a `shooting` slice is registered only when `n_shoot_targets > 0`
  - `ActionHandler.best_action_toward(dx, dy, max_step_length=None)` for scripted policies; never hardcode action counts — use `ActionHandler.n_actions`
  - `ActionHandler.best_advance_toward(dx, dy, advance_roll, ...)` is its Advance sibling. It returns **None** when the scenario registers no advance slice, when the slice is darkened, **or when the turn's roll leaves no legal rung**, so a scripted policy can call it unconditionally and fall back to a normal move. Pass the unit's own `model.advance_roll` — rungs are **absolute** (`M + (bin+1)×(6/bins)`, i.e. 8"/10"/12" at M=6 with three bins) and the roll decides which are *legal*, not what an action means. ⚠ A rung is legal only for a unit that DECLARED an advance in the command phase (`ActionHandler.declare_move_types`, resolved from the unit's lowest-indexed alive model); `STAY` there declares `normal`. See [docs/movement.md](../../../docs/movement.md) § Move types
- `DistanceCache` pre-computes model-objective distances each step; `min_distances_to_same_group` is vectorised and its `.min()` is a *selection*, so a `where(..., inf).min(axis=1)` rewrite stays bit-identical
- **A per-model calculator is called once per model, so anything it computes that does not depend on `model_idx` must be memoised.** Two calculators were ~80% of a 25v25 `env.step()` for exactly this reason. Key the memo on `ctx` identity — a fresh `StepContext` is built every step and held by the env — and give **each cached quantity its own key field**: sharing one key across two quantities computed at different points in a step freezes the later one at its first value. `objective_hold` and `group_cohesion` are the reference patterns; `just measure-throughput` shows the per-calculator split
- Reward: `RewardPhaseManager` (phased reward only); battle-over logic in `domain/termination.py` (`env_components/termination.py` is a re-export plus `get_termination(distance_cache)`)

## Game timing and phases

- `skip_phases`: list of battle phases to auto-advance (default: all non-movement). `max_turns = n_rounds × (5 - len(skip_phases))`; default is 1 step per round (movement only). Set `skip_phases: []` for full per-phase stepping (5 steps per round).
- After the player's turn, the opponent's full turn is auto-executed before the next observation. Turn order: `turn_order` (player / opponent / random).

## Terrain and cover measurement

- `terrain` (fixed list) and `random_terrain` (regenerated each reset) are mutually exclusive. Generation lives in `domain/terrain_placement.py`, called from `place_for_episode`
- **`random_terrain.count` is fixed while size and position vary** — `observations_to_tensor_batch` stacks terrain, so a varying piece count cannot be collated. `mirror: true` keeps the two fixed deployment zones on equal ground; `mirror_mode` picks how (`reflect_x`, the default, or `rotate_180`, which is the symmetry the authored tables are actually built on — under it the odd piece is centred in *both* axes). `angled_fraction` rotates that fraction of small pieces off-axis; a rotated piece is fitted to its **bounding box**, never the centroid-symmetric box, or an asymmetric outline outgrows the allotment it was sampled for and overlaps a neighbour. Both default to the existing behaviour
- **`map_pool` is the third terrain mode, and the only one that trains on real tables.** `terrain` is one fixed board, `random_terrain` a generated one, and `map_pool` draws a whole layout — terrain *and* objectives — from a directory of `TerrainMapConfig` files, one per episode. All three are mutually exclusive; combining them is rejected at load, because one would silently overwrite the other. `MapPool` (`envs/map_pool.py`) parses every file, builds every polygon and runs every check **once at construction**, so a draw is an index; `place_for_episode` takes the drawn `MapLayout` as a plain domain value, which is what keeps the filesystem out of `domain/`. The draw comes off the layout RNG, so a seeded reset picks the same table twice, and `env.map_name` attributes an episode to it. A map that carries terrain alone falls through to the scenario's own objective placement, run against *that* layout's ruins. **`names` is the split and it is why the field exists**: training on every map leaves no layout the agent has not seen and makes a transfer number meaningless — `configs/experiments/25v25_real_maps.yaml` trains on 36 and holds out every table whose number is divisible by 5. **`map_pool.mirror` (default off) draws each layout in one of four orientations**, off the same RNG so a seeded episode still reproduces, and the name gains an `:x` / `:y` / `:xy` suffix so an episode stays attributable to its source table. Expect exactly **2x, not 4x** — the generated tables are point-symmetric to the measurement floor (median 0.00in from their own 180-degree rotation, worst 0.71; the hand-traced ones sat 1.7 out), so `rot180` is the identity and the `xy` flip IS the table while `x` IS `y`. Held-out tables stay held out: `names` filters at load, before any mirroring. Objective *count* varies per episode across a mixed pool, which `Battle.set_objectives` handles by mutating the list in place (the env and the renderers hold that list object from construction, so rebinding it would leave every alias on the previous episode's objectives)
- **`objective_budget` / `terrain_budget` pad the observation so layouts of different sizes share one network.** Objective count is otherwise a hard input dimension (the per-model block is `2 + n_objectives * 2` wide), and piece count cannot collate — which is why the 45 real maps, carrying five objectives and 16 pieces each, can neither be batched together nor scored by a checkpoint trained on the generated scenario. Padding is marked, not implicit: the objective token gains a trailing `present` column and the per-model block one presence flag per slot beside its padded distance pairs, since a padding slot's `(0, 0)` delta would otherwise read as "standing on it"; terrain needs no new column, because its vertex count is zero only on padding. Both default to None and are then byte-identical to a config without them; setting either changes the embedding shapes, so old checkpoints fail loudly. Validation rejects a budget below what the config declares, and the builder refuses a layout that outgrows one at reset — `config_for_map` raises `number_of_objectives` by assignment, which Pydantic does not revalidate
- **Fixed real layouts live outside the config**, in `configs/evaluation/maps/` as `TerrainMapConfig` files (a name, footprints, and optionally `objectives`). `just measure-maps` swaps one onto a scenario for final evaluation, clearing `random_terrain` as it does — leaving the generator on would regenerate a layout at reset and silently discard the map. A map's `objectives` replace the scenario's along with `number_of_objectives`, and clear `objective_min_separation` / `objective_terrain_clearance`, which govern the random draw the map replaces; every entry must be *determined* — an `area` outline or x/y — since `place_for_episode` honours fixed positions only when *all* of them carry coordinates, so one undetermined entry would silently randomise the rest. On the 45 shipped maps the objective **is the ground**, and since 2026-08-20 the tables are generated by `just fetch-maps`: terrain from the public layout API, objectives resolved from `scripts/objective_markers.json`. **The API's own objective markers are NOT used** — they disagree with the published layout cards on six of the 45 tables by 12–18 inches, which is a different ruin entirely, and neither the layout's copy of its deployment nor the deployment's canonical markers is right everywhere. Its *terrain* is fine and matched 45/45. An objective is a **ruin** — terrain pieces sharing at least 1" of boundary, since the layouts split one rectangle along a diagonal or butt two bars into an L; resolving to the nearest *piece* made 30 of 225 objectives cover half a ruin. A position takes the **largest unclaimed ruin within `MARKER_REACH_IN` (4.5")**, not the nearest and *not* the rules' 3" control range — an authoring distance sitting in a measured trough, since a control-range cutoff handed objectives to 12.9 sq in slivers while 82.5 sq in ruins stood 4" away. **A position equidistant from two equally large ruins designates both**, which is why a table carries five *or six*: the boards are point-symmetric, so the centre position routinely sits between a ruin and its own reflection, and the published cards draw that as two Centre icons. There are **no disc objectives**. Checked against the published cards at 45/45 within 3", counts 24 fives and 21 sixes, zone split exactly 82/82/82 — see [configs/README.md](../../../configs/README.md), including why this saturates the scripted bar
- **A map brings its own DEPLOYMENT ZONES, and they are outlines not rectangles.** `deployment_zone` is `(x0, y0, x1, y1)` and **only two of the six real deployments are axis-aligned bands** (`long_edges` and `short_edges`, 11 of the 45 tables) — one is a pair of triangles split by a board diagonal, two are stepped staircases, one is bounded by arcs. `TerrainMapConfig.deployment` carries a name and two role outlines; `MapLayout` carries them into `place_for_episode`, and `WargameEnvConfig.deployment_outline` / `opponent_deployment_outline` carry them on the *evaluation* path, which installs a map onto a scenario and has no layout — wiring only one route would train a map under its own deployment and score it under the rectangle. Sampling still happens in the rectangle, which becomes the outline's **bounding box**, and `_fits_in_zone` rejects anything outside; the base is checked at four cardinal points, since an outline has no bounds to inset the way the rectangle path does. Zones travel with a mirrored layout or a flipped table deploys its army on the far side of the board. **Unlike the API's objective markers, its zones are trustworthy** — the published layout cards' tinted region is ≥98% inside the API polygon on all 45 tables. Names are ours (`diagonal_halves`, `long_edges`, `opposed_quadrants`, `short_edges`, `stepped_bands`, `stepped_columns`) and `long_edges` is the outlier worth watching: it faces the armies across **20 inches of the short axis** against 24–40 elsewhere, which at a 12" weapon range is a different game from turn one. **Placement and RENDERING are two separate wirings and both are needed.** `place_for_episode` hands the outlines it resolved to `battle.set_deployment_outlines`, `BattleView` exposes `deployment_outline` / `opponent_deployment_outline`, and the v2 and human renderers draw the polygon when there is one. Without that second half the renderers can only draw `deployment_zone`, and for a whole training run they tinted the old left-hand band while the army stood along the bottom edge — placement was right the entire time. The env exposes them as *properties*, unlike `deployment_zone` which is copied to an attribute at construction: a pool draws a new map every episode. The outlines also ride on the snapshot (schema 2.5, optional) so `replay-render` keeps them. A map with no `deployment` block uses the scenario's rectangle, the exact no-op
- **Piece count is what makes cover available, not coverage.** `just measure-terrain <config>` reports *cells hidden from a squad* — the only number that matters, because exposure is "at least one enemy sees me". Batch 1/2's 7 pieces of 5-7 scored 0.058; 29 pieces of 3-7 scores 0.198 at similar coverage. Many small pieces beat few large ones. Tune a profile there, not after a training run
- The packing validator bounds the **expected** footprint, not the worst case — bounding worst-case-square rejects exactly the wall-shaped specs it should allow. `_MAX_LAYOUT_ATTEMPTS` is the real backstop
- `track_exposure: true` accumulates `env.exposure_rate`, `env.terrain_proximity` and `env.firepower_ratio` (`env_components/exposure.py`), all from one `compute_threat_counts` scan per shooting phase — it returns a `ThreatCounts` namedtuple with both threat counts and both "has a target" masks. All are `None`, never `0.0`, when unmeasured — 0.0 would read as "never exposed"
- **Prefer `firepower_ratio` to `exposure_rate`.** Exposure counts only our side, so it falls both when a policy manoeuvres and when it hides; the ratio of shooters separates them. LOS is exactly symmetric (`wargame.py` sorts endpoints to guarantee it) but symmetry is *pairwise* and does not equalise the counts — which is what makes cover worth using at all
- **Count shooters, not targets.** Because LOS is symmetric, an exposed model is exactly a model that can fire, so "enemies we can see" is *their* shooter count. The metric's first version had this backwards and scored `random` top of the table; see [docs/metrics.md](../../../docs/metrics.md) § Cover metrics
- `exposure_rate` deliberately ignores engagement-range gating, and averages over *alive* models so casualties lower it on their own. See [docs/metrics.md](../../../docs/metrics.md) § Cover metrics before comparing it across configs
- **`observe_objective_control` puts per-objective control state on the objective token** (player count, opponent count, radius; 2 → 5 dims, default off). VP is scored on `player_count > opponent_count` per objective, but an objective otherwise reaches the network as *nothing but a location*. Two reward levers keyed on those counts — `closest_objective_v2`'s overstack penalty and `objective_hold`'s `surplus_value` (since removed) — each halved objective occupancy on both seeds, a penalty and a discount failing identically — neither was attributable without this input, so the policy could only experience either as "objectives pay less". The lever that finally worked, `objective_hold.crowding_exponent`, keys on the same counts and is configured alongside this flag for that reason. Widening the objective token is safe (no `_alive_feature_index` trap); turning it on changes the embedding shape, so old checkpoints fail loudly. ⚠ **The count on the token is the count VP scores, and until 2026-08-22 it was not.** The builder had its own membership test — `area.contains_points` on the model *centre* — against scoring's `norms_offset <= obj_radii`, measured from the **base edge**; they disagreed on **7.6% of (objective, step) slots** (206 of 2,700, held-out nine). All three readers now share `objective_counts_from_norms_offset`, pinned by `tests/test_observed_control_matches_scoring.py`
- **`observe_unit_strength` puts a unit's alive fraction on every one of its models' tokens** (per-model block, inside `core` ahead of `alive`; default off, byte-identical off). It exists because the shooting head mean-pools opponent tokens into one token per unit and a mean is invariant to how many terms it averages, so a full squad and its last survivor pooled identically — the target choice keys on a count no tensor carried. Constant across a unit's members, so the pooling and projection are unchanged. **Untrained, and its cheapest proxy is null**: a scripted policy firing at the *weakest* valid unit rather than the nearest scores +1.7 ± 5.7 vp_margin paired over 100 identical layouts (t = 0.30, ahead in 24 of 100), where the *unpaired* 60-episode read of the same comparison said +8.0. The choice is common (59.5% of shooters see more than one valid unit, 72% of those see differing strengths) — it just does not pay, because unit targeting discards only 3.6% of declared attacks, which caps what finishing a unit early can reclaim. Use `just measure-paired` for any comparison this size; two `measure-baselines` rows cannot resolve it
- **There is no line-of-sight input in the observation.** `observe_threat_count` added one and measured null across both seeds of batch 3, so it was removed. A per-model threat *count* says how many guns bear on a model but not from where, which cannot support "step two cells left and the wall covers me". A directional encoding is untested
- **Shooting targets a *unit*, not a model.** The action slice is one entry per enemy unit (`unit_count`, 25 -> 5 on a 25v25 board) and the defender allocates each attack to a model still standing, so an attack is lost only when the whole unit dies — 3.6% of declared shots, against 36-40% when a weapon named a model. Target legality checks visibility and range **independently** across the unit, and cover is unit-level and all-or-nothing: one model in the open denies it to everyone. The transformer pools opponent tokens into unit tokens at the shooting head, **excluding the dead** — otherwise a destroyed model's latent leaks into its unit's token and defeats the key-padding mask at the last step
- **`group_id` is this project's name for the rules' *unit*** — the vocabulary was chosen to keep the project's own, and it is the rules concept wherever one is needed. Models in a group ignore each other, and their target's group, when tracing sight. There is no second identity for this; adding one would duplicate the concept. **Numbering is per army**, so player group 0 and opponent group 0 are different groups — compare through `sight.group_keys`, never raw ids, or each side's first squad silently ignores the other's
- **Models do not occlude — only terrain does — and partial cover is a real state.** Not occluding is a **deliberate divergence** from `docs/rules/06-visibility-and-damage.md` (recorded in the gap map): no model here has an opaque silhouette, since a 32mm infantry figure is a thin shape on a round base rather than a cylinder, so a line that clips a base can be drawn in practice. It takes the rules' *ignore your own unit* exemption with it — that exemption exists only to stop a squad shielding itself from its own occlusion, so with nothing occluding there is nothing to exempt, and `Occluders` / `group_keys` / `sight_between` / `segments_clear_of_discs` are all gone. **It is not a small change:** on `25v25_shooting_opponent.yaml` over 100 identical layouts the bar (`squad_march_shoot`) goes **+38.0 → +17.0 vp_margin** and 0.75 → 0.65 win, because the opponent shoots more freely too; every baseline on every config predates it. `base_radius` still shapes sight in one way — it sets the corridor width, which is what lets terrain grant cover. Three rays per pair — the centre line and two parallel to it, offset by the wider of the two bases. All clear is visible, none is hidden, anything between is **cover**, which worsens the attack's Ranged Skill by 1 — so cover is a fact about *terrain*, granted by a ruin that clips part of the corridor. The offsets are parallel and symmetric in the pair rather than tangents to the target: the literal tangent construction is directional, and `firepower_ratio` / `exposure_rate` are built on sight being exactly symmetric. **Cover is a no-op at `base_radius: 0`** — the three rays coincide — which is why every pre-base result still reproduces. Note the *mask* decides visibility on the centre ray alone (it is handed positions, and a corridor needs the pair's radii); the corridor answer is asked separately by `_unit_cover`, which has the models
- **Sight is a sampled ray, and the seam is a matrix.** `domain/los.py` is the geometry primitive (segments × samples × blockers in one vectorised pass); `domain/sight.py` composes it with the terrain rules. `BattleView.line_of_sight_matrix(origins, targets, candidates)` is the real entry point and `has_line_of_sight_between_points` is a single-pair convenience — **calling the single-pair form in a loop is the shape that measured a 3x regression**, so the shooting mask and the exposure scan take the matrix and pass a `candidates` mask so range gating rules pairs out before they are traced. `los_sample_step` (config, inches, default 0.25) is the resolution guarantee: a blocker thinner than it can fall between two samples and leak sight. Samples sit at **absolute** distances along each segment, so a pair's answer never depends on what else was in the batch — deriving them from the batch's longest segment is cheaper and made splitting a query change its result
- `reset(options={"combat_seed": n})` seeds the dice independently of the layout. The derived draw still happens either way, or the placement stream would shift and the two would stay entangled. `just measure-noise-floor` uses it; on 25v25 the dice contribute *more* spread than the scenario does
- `reset(options={"augment_start": True})` opts in to `start_on_objective_probability`, the training-time start-state augmentation (one squad begins on an objective). **Opposite discipline to `combat_seed`: it draws *nothing* when not requested**, so a config carrying the field produces layouts bit-identical to one without it. That is what keeps an augmented run's evaluation comparable to a bar measured on the base config. Opt-in rather than opt-out on purpose — a training loop that forgets to ask trains the bit-identical control, which is obvious, while an evaluation that forgot to switch it off would score a different scenario and look plausible doing it. Only the *parallel* PPO rollout passes it; `num_rollout_envs == 1` raises rather than silently training the control
- `objective_min_separation` / `objective_terrain_clearance` constrain random objective placement (rejection sampling in `objective_placement`, best-effort). Both default to `None` = the historical draw, which overlaps discs in 25% of episodes and puts 11% of objectives inside a ruin. **Enabling either changes the scenario distribution — runs with and without are not comparable**

## Placement (`ModelConfig`/`ObjectiveConfig` in YAML)

- No key → full auto · Key without x/y → random + config attrs · Key with x/y → fixed
- Properties: `has_fixed_model_positions` / `has_fixed_objective_positions` / `has_fixed_opponent_positions`

## Opponents

- Reuse `WargameModel`/`ModelConfig`; YAML keys: `number_of_opponent_models`, `opponent_models`, `turn_order`, `opponent_policy`
- `TurnOrder`: `player`/`opponent`/`random`
- Policies in `envs/opponent/`, registry: `RandomPolicy("random")`, `ScriptedAdvanceToObjectivePolicy("scripted_advance_to_objective")`, `ScriptedAdvanceAndShootPolicy("scripted_advance_and_shoot")`, `ScriptedBaselineOpponentPolicy("scripted_baseline")`, `NetworkOpponentPolicy("model")` — the last registered from `model/opponent/`, so it is present only once `create_environment` (or anything importing `wargame_rl.wargame.model.opponent`) has run
- **`scripted_baseline` plays any registered *baseline* on the opponent side**, named by a `baseline` param. It does not reimplement anything: the baseline is handed a `MirroredEnv` (`envs/opponent/mirror.py`) with the two sides swapped, and its `shoots` is derived from whether it overrides `select_shooting`. A new baseline that reads a side-specific env attribute has to be mirrored — `tests/test_scripted_baseline_opponent.py` scans for that and fails. **The opponent was most of the ceiling**: against `squad_march_take` the old bar `squad_march_shoot` falls from +104.9 to −5.6 vp_margin and every weaker policy is annihilated — see [docs/opponent-policies.md](../../../docs/opponent-policies.md)
- New policies: one class per behaviour, `Scripted` prefix, register as `"scripted_<name>"`; implement `select_action(opponent_models, env, action_mask=None)`
- Read env state through the public properties — `opponent_action_handler`, `player_action_handler`, `last_player_shooting_results`, `last_opponent_shooting_results`, `last_player_fight_results`, `last_opponent_fight_results`, `terrain` — not the private attributes
- A policy that fires must set `shoots = True`; only then does the env overlay range/LOS/engagement validity on its mask (`_opponent_action_mask`). Nothing downstream re-checks legality — see [docs/shooting.md](../../../docs/shooting.md)
- `scripted_advance_and_shoot` and `random` both shoot back (`shoots = True`); `scripted_advance_to_objective` does not. Switching a config to a shooting opponent invalidates every baseline and agent score measured on that config
- `number_of_opponent_models=0` (default) → no policy, env unchanged
- **`scripted_advance_to_objective` parks permanently.** It returns `STAY` unconditionally once inside an objective radius, so measured total opponent displacement is exactly 0.0 from round 9 onward, and its 0.3 centroid blend leaves **at least one objective with zero opponents in every episode**. Its final allocation is a deterministic function of initial positions, so it is predictable at reset. Exploiting that is *less* effective than it sounds — see `contest_and_spread` in `baseline/`, which does exactly this and still loses to `squad_march_shoot`

## Rendering

- `"human"` (Pygame) / `"rgb_array"` (video); renderer injected via constructor
- Player: blue/green circles · Opponents: red/warm triangles
- Use a single FPS cap for human rendering; avoid phase-conditional throttle — it breaks when default stepping changes (e.g. skip_phases)
- **Two renderers**: legacy `renders/human.py` (`HumanRender`, the default) and `renders/v2/` — a `Scene`→`Backend`→`Presenter` split (`build_scene` is domain-free, `control.py` isolates the ownership/LOS domain reads, a swappable `RenderBackend` draws, interactive/recording presenters). Pick via `renders.v2.build_renderer(name, mode, backend=...)` (`name="legacy"|"v2"`); `simulate.py` exposes `--renderer/--mode/--backend`, the record callback takes `renderer_name`/`backend`. `name` defaults to `legacy` for `build_renderer`, but **`RecordEpisodeCallback` defaults to `v2`**, so training recordings show bases, polygon terrain, area objectives, tracers and the HUD. Recording depends on the `FrameSource` protocol (in `renders/renderer.py`), which both satisfy — do **not** add abstract methods to the `Renderer` ABC. Legacy `human.py` is frozen as the A/B baseline (`tests/test_terrain_render.py` depends on it)
- **v2 drawing backends** (`renders/v2/backends/`): `pygame` (aliased, the legacy look), `pygame_aa` (3× supersample → `smoothscale`) and `pillow` (`PIL.ImageDraw`, antialiased fills natively). `pillow` is the **default** — the Phase 2 bake-off (`just render-bakeoff`, `scripts/render_bakeoff.py`) found it antialiases as well as the supersampled backend at ~pygame speed (1.04–1.09× vs 3.9–5.9×). All three rasterise the same `Scene`, so any difference is edge/text quality, not primitives. Add a backend by implementing `RenderBackend` (`renders/v2/backend.py`) and wiring it into `factory.build_backend` + `factory.BACKENDS`. The interactive window presents via the backend's `to_rgb_array`, so a non-pygame canvas displays too
- **v2 themes** (`renders/v2/theme.py`): a `Theme` is a `Palette` (every board/HUD colour) plus panel metrics. `DEFAULT_THEME` mirrors the legacy colours (the A/B baseline); `TABLETOP_THEME` is a parchment-board look — player-blue vs opponent-red shade ramps, sage/terracotta control washes, warm dark HUD. Select by name from the `THEMES` registry: `build_renderer(..., theme="tabletop")` (accepts a `Theme` or a name via `resolve_theme`); `simulate`, `replay_events.py render` and the record callback expose `--theme`; `simulate` and replay default to `default`, but **`RecordEpisodeCallback` defaults to `tabletop`**, so a training video reads as two armies rather than a rainbow — every player squad is a shade of blue and every opponent squad a shade of red, where `DEFAULT_THEME` gives the player blue, green, yellow, purple, cyan, orange, pink and red and a player squad can share a colour with an opponent one. Pinned by `test_the_tabletop_theme_is_blue_against_red`. Two renderer conventions apply to all themes: **the grid is a substrate** (drawn above the opaque zone fills but below terrain, objectives and models — pinned by `test_grid_is_drawn_under_terrain_and_models`), and **both sides are circular bases** (real bases are round; colour carries the side, via the shared `_draw_models` helper)
- **v2 HUD** (`presenters/base.py`): a top three-zone panel — **objectives** (per-objective control pips + held tally), **victory points** (per-side VP with the margin as a centred, bold hero), **forces** (alive/total + strength bars) — over a bottom three-column panel — **clock** (drawn clock icon, `R n/N`, a round track, and a two-slot **turn-order** field — `YOU > OPP` or `OPP > YOU`, the first side bold and side-coloured — and a **rewind-depth** readout `[,] n`, drawn only when the presenter can rewind), **reward** (the step's signed reward as the hero, the episode total, a composition bar and a paid/charged count), **context** (`PAUSED` interactively, `run_label` + `epoch` in a recording; the key hint sits under it and is `None` in a recording, where nobody can press one). Data rides on `HudData` (control counts, held, alive), populated in `build_scene` from the view, so it works live *and* in replay. HUD text is drawn in a monospace face (`renders/v2/fonts.py` resolves it, falls back to the default if none) with fixed-width slots so numbers never shift as they tick; side accents use `Palette.hud_player`/`hud_opponent` (bright, legible on the dark panel — distinct from the board group colours). The top panel is two rows tall, so a v2 frame is taller than legacy's — the whole-frame A/B parity test was narrowed to a board-region check. **Two things in the south panel are deliberately independent of the config**: the round track holds a fixed 170px, drawing one segment per round only while segments stay wider than the gaps and degrading to a continuous fill past ~28 rounds; and the reward is summarised by a composition bar (one segment per calculator, width = magnitude, colour = sign) plus `+x from n` / `-y from m`, which is O(1) in the number of reward terms — a phase may declare any number, and the per-calculator names belong in the (not yet built) overlay rather than in the bar. `reward_breakdown` keeps the phase's *declaration* order so segments never swap seats between frames, and drops `parent/child` sub-component keys, which sum into their parent and would otherwise double it. The clock icon is drawn from primitives because the resolved fallback font may have no such glyph. **The turn field shows turn *order*, not whose turn it is now** — that question has one answer in every frame ever drawn, because `run_after_player_action` executes the opponent's whole turn inside the player's `step()` and the clock is always parked back on a player phase before a frame is composed. Order is what varies: under `turn_order: random` the player's side is re-rolled every `reset`, and it decides whether the positions on screen already include the opponent's reply. `scene.player_acts_first(clock.active_player)` derives it, reading the *active* side as the player's own — sound only because of that same invariant, which `tests/test_debug_session.py` asserts rather than trusts. Works in replay for free: `ClockSnapshot.active_player` has always been recorded, so no schema bump. **The rewind-depth readout is state, not an event, and that is the point** — a real session logged `Nothing to step back to.` twelve times to a terminal nobody was watching while the window said nothing at all, so the count is drawn where the user is looking and dims at zero, answering "will this key do anything" *before* it is pressed. Depth is not battle state, so `HudData.undo_depth` is grafted on by `DebugPresenter._scene_for` via `dataclasses.replace` rather than threaded through `build_scene`, and stays `None` for the recorder and replay, which cannot rewind at all. **Keys live behind `[Tab]`**: each presenter declares its own in `key_map()` as `(key, action)` pairs, and that one list feeds both the centred overlay (`BasePresenter._draw_key_map`, drawn over a dimmed frame) and the panel's single `[Tab] keys` hint — so the panel names one key however many are bound, and a presenter with no keys (recording) gets neither. Key names are written in brackets everywhere they appear, including the replay timeline strip.
- **v2 shooting** (`scene.py` `_draw_shots`): a shot that *did damage* draws a tracer from the shooter's base edge to its target's, plus an impact ring on the target scaled by the damage; a killing shot is heavier with a `Palette.shot_kill` ring. Tracer colour is `shot_player`/`shot_opponent` — by **side**, not by squad, since the group ramp already answers "which squad". **Misses are deliberately not drawn**: a 25v25 volley is ~21 shots of which ~4 land, and drawing the misses (full length *or* as muzzle stubs) buries the ones that did something — measured by rendering five variants of one real volley. Removing the movement arrows instead barely helps, so the arrows are not the clutter. Volleys **fade over `SHOT_FADE_FRAMES`**, because the env keeps the last results until the next shooting phase and an un-faded tracer makes a movement frame look like a firefight; each presenter ages the volley by *content* (the env returns a fresh list each call, so identity is not enough) and `ReplayPresenter` computes age by walking back from the current index, since the timeline is scrubbable. Built from `Seg` + `Disc`, so no backend changed. `killed` rides on the snapshot from schema 2.3
- **`board/` is a LEAF, and the sampling grid lives there** (`board/grid.py::board_grid`, promoted from `control.py::_cell_centres`). It may import `domain/` and `types/` and nothing else; `tests/test_board_layer_is_a_leaf.py` pins that with an AST walk, and pins that **only `renders/v2/control.py`** may import it — v2's single domain seam. The grid moved because the threat overlays and the threat *field* must sample the same cells or they disagree about the same ground while both look right, and `board/` cannot import the renderer to get it. `tests/test_board_grid.py` asserts the promoted function is cell-for-cell the old private one, edge clamp included, because two shipped overlays are pixel-pinned to that arithmetic and a changed centre would surface as an unrelated overlay failure.
- **The `[T]` threat FIELD is a different question from the `[R]` threat REGION, not a better answer to it.** ⚠ **The opponent moves before it shoots**, so `[R]` — range ∩ LOS from where models *stand* — reads **FALSE-SAFE** for anyone choosing where to end a turn: a cell behind a ruin is shot from beside that ruin one move later. `[T]` (`board/threat.py::threat_field`, `ThreatHorizon.next_turn`) traces sight from **every cell a shooter can reach**, and its scalar is expected **casualties** to one reference model, not wounds and not a count (`observe_threat_count` was a measured null, and a count is structurally wrong where the sides carry different guns). Measured on the golden config's held-out nine: `[R]` calls **18.7%** of the board clear where `[T]` does not, and mean casualties per cell roughly doubles. Both switches exist and both are off by default. `ThreatHorizon.current` is kept only to reproduce `compute_threat_region` exactly — which is the equivalence test that pins the whole module — and to *measure* that gap; reading it to choose where to stand is the error the module removes. **The two-hop is affordable only because sight is terrain-only**: `VisibilityCache` is a `(Q, Q)` bool built once per *table* and reused for every turn of every episode on it (~10 s at 1", ~0.6 s at the overlay's 2"; gated at the longest weapon range and **not** range + move, since the move is spent reaching the origin cell). Bands are **disjoint quantile slices** run through the existing `_rings_from_mask` + `_chaikin` path — nested "above q" level sets would double their alpha where they stack, the same trap `DiscUnion` exists for — and are drawn **under** the `[R]` outlines, because a wash over a line hides it. ⚠ **Cover is not applied and cannot be**: the three-state `visibility_matrix` is not on `BattleView`, and a grid cell **has no base radius** while the cover predicate is defined by offsetting rays by the endpoints' radii. The bias runs against objectives specifically (every marker on the real tables is inside a ruin), so read it beside `just measure-hold-hazard`. ⚠ **A REPLAY draws nothing**: the snapshot records every weapon and defensive stat but **not per-model Move**, which is what the reachable set is built from, and a field traced at a guessed Move is wrong in the false-safe direction — `can_price_threat_field` gates it and `test_a_replayed_frame_is_the_field_off_frame` pins that degrading means *identical*, not "did not crash"
- **The unit matchup table is a REDUCTION of `domain/shooting.py::expected_damage_matrix`** (`board/matchup.py`, `just measure-matchups`), never a second implementation of it — that matrix is already hstacked onto every player model token, so a separate calculation could disagree with what the network was shown. Attacker axis **sums** (every model in the firing unit shoots), defender axis does **not** (one representative model takes the maths); backwards, a 5v5 cell reads 25× the truth, which is the easiest mistake in the module. ⚠ **Expected damage is DAMAGE POINTS, not models**: excess damage does not spill between models *and* a model may absorb several hits, so a model costs `D × ceil(W / D)` points — every shipped config is `damage: 1 / max_wounds: 1`, where both effects are invisible and the two columns are the same number. ⚠ **Unlike everything else in `board/` it has NO POSITIONS**: range never enters the damage scalar, only `reach_margin` / `free_rounds` / a two-distance exchange ratio, and a unit whose members do not share a profile is **refused** rather than averaged, since the mean of two stat lines is a model nobody has
- **v2 threat overlays** (`control.compute_threat_overlay` + `DiscUnion` in `scene.py`, `[R]` / `[E]`): two things the renderer never drew — how far each side **reaches**, and where it is **engaged**. Both merge **per side**, not per squad, and take the side's colour like the tracers do: a group ramp answers "which squad", and a merged shape is one army's reach. **Shooting threat is range ∩ line of sight, sampled on a grid** — `line_of_sight_matrix` with a `candidates` mask, the same predicate the shooting mask uses, so the picture cannot disagree with the rule. **The range gate is not an optimisation**: `domain/sight.py` builds its pair list from `np.nonzero(candidates)`, only 12–16% of pairs survive a 12" gate, and a gated ray is ≤48 samples against up to 296 — so a per-side sweep is 66–105 ms against **3.0 s** ungated, i.e. cheaper than the single-observer `[S]` shadow that already ships. It deliberately does **not** gate on `advanced_this_turn` or on the shooter being engaged, following `compute_threat_counts`: those describe whose turn it is, not who is dangerous. The boolean grid becomes closed rings by cell-edge extraction — a hole is just another ring, which is why an outline needs nothing `Poly` cannot express. ⚠ **Never collinear-collapse a ring before smoothing**: Chaikin moves a vertex by a quarter of its *adjacent segment length*, so collapsing a 20-cell run along the board edge into one 20" segment hauls the boundary ~5" inward and swallows the models standing on it (found by eye, 4 of 25 models, edge-only — `test_no_alive_shooter_falls_outside_its_own_threat_region` is the trap). Keeping the cell vertices bounds it, and the displacement **converges** to exactly ⅛ of a cell (0.063 / 0.094 / 0.109 / 0.117 / 0.121 at 1..6 on a 1" grid), so smoothing harder costs vertices and never fidelity. **Engagement radius is `engagement_range + 2 * base_radius` off `rules_quantities`, never `model.base_radius`** — the gate uses the config's resolved global, and a per-model reading would agree today and diverge silently. `DiscUnion` exists because every backend gives each translucent primitive its own alpha layer, so N discs double their overlaps; it paints them into one layer and composites once (cheaper than the discs it replaces, and holes come free). The threat outline carries a **`threat_fill_alpha` wash** — outline-only was the original spec and on a real board it does not say which side of the frontier is threatened, nor show the band where the two reaches overlap. **Configured by `ThreatOptions`** (`show_threat`, `show_engagement`, `spacing`, `smoothing`), validated at construction and threaded through `build_renderer(threat_options=...)`; `factory.threat_options()` is the one CLI parser for `simulate` / `play` / `debug` / `replay-render` / `train --record-*-range`. **Deliberately not a `WargameEnvConfig` field** — every config model is `extra="forbid"` and the config is the *scenario*; a visual switch there would change what a video looks like for a given config forever. Off by default everywhere, and `build_scene` with no `threat` argument is pinned byte-identical to before the feature existed. **Replay draws them too, and traces its own sight to do it.** `_SnapshotView` holds the real `domain.terrain.Terrain` (not a stub) and a `line_of_sight_matrix` delegating to `domain.sight` through `control.sight_matrix_from_terrain`, so a replayed region is the live one *exactly* — pinned by `test_a_replayed_threat_region_is_the_live_one`, the only test that catches a lost `los_sample_step`, a dropped `blocking_mask` or a weapon-range derivation that disagrees with `max_weapon_ranges`. Weapon range needed **no new field**: `ModelSnapshot.weapons` already recorded `weapon_range` for both sides. Schema **2.6** adds `RulesSnapshot` (`engagement_range`, `base_radius`, `los_sample_step`, `blocking_mask`) in *units*, populated in `build_snapshot` so it lands on the live and recorded copies alike — a field only on the recorded one would break the replayed-equals-live invariant `test_v9_milestone_validation` pins, which is exactly why `EpisodeProvenance` is header-only and this is not. Pre-2.6 recordings replay **pixel-identical to overlays-off**; guessing a sample step would answer a different question convincingly. ⚠ `ReplayPresenter` composes through `build_scene_from_snapshot`, **not** `BasePresenter._scene_for`, so an overlay wired only into the latter computes correctly and never reaches the frame — every unit test passed while the replayed frame came out untouched, and only `test_the_overlay_actually_reaches_the_replayed_frame` (a pixel comparison) caught it
- **v2 replay** (`renders/v2/replay.py`): plays a recorded match back through the *same* `build_scene`. `build_scene_from_snapshot` adapts a `GameStateSnapshot` to the read-only surface `build_scene` reads (backing polygons with the real `Polygon` value object), so a replayed frame is bit-identical to the live one — control is precomputed (`objective_control`) and terrain rides on the snapshot (`terrain_footprints`, schema 2.1), as do the reward ledger and `skip_phases` (`reward.episode_total`, schema 2.2), so no env is rehydrated. `ReplaySource.from_controller` materialises the snapshots + anchor indices; `ReplayPresenter` reuses `BasePresenter._compose_scene` (split out for this) and adds a scrubbable timeline + play/pause + MP4 export. Driven by `replay_events.py render` / `just replay-render`
- **v2 debug stepping** (`presenters/debug.py` + `envs/debug/`, `debug.py` / `just debug`): a live match the caller steps by hand. `InteractiveRenderer` pauses by spinning inside its own `render()`, so the driving loop never learns a pause happened — stepping is therefore **a change of ownership, not a keybinding**. `DebugPresenter` subclasses it, `render()` advances one frame and returns, and keys are reported through a shared mutable `DebugControls` (`paused` / `step_once` / `step_back`) that only the *driver* clears, so a key pressed between frames cannot be dropped. `Renderer.render` stays `-> None` and the ABC gains nothing. The split across two packages is forced by dependency direction: the presenter reads a `BattleView` and lives under `renders/`, while the undo stack and `run_session` touch `WargameEnv` and so sit beside `baseline/`. **Rewind deep-copies the env rather than round-tripping a `GameStateSnapshot`** — `load_state` restores neither the combat RNG nor terrain and *deliberately* clears the reward-shaping memory, which scores the same action `0.0` against a live `-0.3` (`base_penalty` zeroed); a rewind that changes the reward defeats the A/B the mode exists for. The renderer is detached across the copy since a window is not copyable. Takes a baseline name *or* a `.ckpt`, both through the existing `ActionSelector` alias — the reason it is worth having over `just play`, which is scripted-only. A config with `skip_phases: []` already steps one *sub-phase* at a time, so intra-round inspection needed no new code
- **v2 debug inspector** (the side panel in `presenters/debug.py`): click any model on *either* side and a reserved column shows its step — position/wounds/stats, its last move as **intended versus actual**, what it earned, what it shot and what shot it, and the observation row the network received. Reserved out of the window by `BasePresenter._reserved_width()` (honoured by both the initial layout and the resize path) rather than drawn over the board. Three rules came out of building the layout against one real recorded step, and each is load-bearing: a **dead model's reward is 0.000** because `phase_manager` iterates *alive* models — printed bare that reads as broken reward plumbing, so the reason is drawn beside it (the rule is pinned by `tests/test_debug_session.py`); **per-calculator numbers are army means**, since `phase_manager` divides by the alive count before the breakdown *and* most calculators return `{}` from `get_last_breakdown(i)`, so a per-calculator × per-model table is not buildable and the column says `ARMY MEAN`; and **intended-versus-actual is the one field nothing else in the renderer shows** — on a real step one model ends 0.73" off its own action vector from `resolve_move` displacement while others sit at exactly 0.00. `MoveRecord`s are built by the *session*, not the presenter: the env keeps only the most recent action, and decoding one needs the action handler that `renders/` may not import. The rewind carries its own move history in lockstep with the undo stack, or stepping back leaves the panel describing a step that was just undone. The selection ring and intent ghost are drawn onto the frame, never through `build_scene`, which is shared with the recorder and the replay adapter — neither of which has a cursor. Extra reads live on `DebugView` (`renders/v2/debug_view.py`), a `runtime_checkable` protocol extending `BattleView`; widening `BattleView` itself would push `last_per_model_reward` and `observation` onto the replay adapter, which can supply neither
- **v2 sight shading** (`control.compute_los_shadow` + `sight_from`, `[S]` in `presenters/debug.py`): shades the board the selected model cannot see. **It samples the engine's own predicate on a 1-inch grid rather than projecting terrain silhouettes** — 2640 rays in one vectorised `line_of_sight_matrix` call, then run-length merged into `Poly` rects, so no `Backend` protocol changed and no primitive was added. A silhouette projection would be prettier, cheaper and exact at the edges, but it would be the *renderer's* answer to "what is hidden", and a disagreement between the renderer and the engine is precisely the bug worth finding — `test_the_shadow_is_the_engines_own_answer_and_not_the_renderers` asserts every sampled cell is shaded exactly when `has_line_of_sight_between_points` says it is unseen. The sweep asks `BattleView.line_of_sight_matrix`, the predicate both shooting masks and the exposure scan use — it is not the shooting *mask*, which also gates on weapon range, and the panel's `SIGHT` section counts enemies under the same predicate so the number and the picture never answer different questions. **Building this is what found that models were occluding on the real shooting path while the unit exemption reached only the exposure tracker**, which is what prompted removing model occlusion entirely; a two-mode toggle written to show the gap collapsed back to one key once they agreed. Merging runs **both** horizontally and vertically, because the fill is translucent and two rects sharing an edge draw that seam twice as dark. Reaches the frame through `BasePresenter._los_shadow()` into `build_scene` rather than being painted on like the selection ring, since it belongs *under* the models in the draw order; a sweep is ~100 ms, so it is cached on (observer position, terrain) — the only two things it depends on, now that models do not occlude — the window polls at 30 fps while paused and nothing about it changes between those frames
- **v2 hand-authored orders** (`envs/debug/session.py` `resolve_order`/`apply_orders` + `debug/overrides.py`, `Click`/`Enter`/`Backspace`/`D` in `presenters/debug.py`): paused, click open ground and the selected model is ordered there. **The click is not the destination** — `best_action_toward` snaps it to the nearest `(angle, speed)` bin, and the ghost is drawn at the *decoded landing point*, which is the honest answer and shows the discretisation the policy is choosing under. **One button, two meanings, decided by what is under the cursor**: a model selects, open board orders, off-board (the panel) deselects as it always did — they never overlap, because empty ground cannot be selected and ordering onto another base is not expressible anyway. Resolution lives in the *session*, not the presenter, for the `MoveRecord` reason: snapping needs the `ActionHandler` and checking needs the action mask, neither of which `renders/` may import — the presenter reports a *board point* (`controls.order_at`) and the session writes back an `Order`. **Legality is the agent's own mask**, so a refusal has the grounds the policy's would; the refusal *message* is not, because "the action mask refuses this move" is true of every refusal and explains none — a casualty (STAY only) and the wrong phase are the two that happen, and `_refusal` names them. An illegal order is still drawn, in the casualty colour: dropping the click silently reads as the tool ignoring you. **The opponent is overridden through its policy, not an action vector** — `run_after_player_action` runs its whole turn *inside* the player's `step()`, so there is no vector left to edit; `OverridableOpponentPolicy` wraps the configured one (copying `shoots`, which the env uses to decide whether to pay for the opponent's LOS mask) and is installed fresh each step, because a rewind hands back a different env carrying a deep copy of whatever was installed when it was captured. **Ordering is movement-phase-only, and the panel says so before the click** — the `ORDERS` head reads `MOVEMENT PHASE ONLY` and the section draws even when empty, because that emptiness is what needs explaining. Same rule as the rewind depth, and from the same evidence: a real session clicked into a shooting phase **thirty times in ninety seconds**, each refused correctly and each explained to a terminal nobody was watching. The loop now also logs one line per *distinct* reason rather than per click. `Enter` is an alias for `.`, not a separate commit: **any** forward step applies pending orders, so a click followed by `.` cannot silently discard them. **Dice are held by default** — the deepcopy rewind restores `_combat_rng` with everything else, so re-running a step reproduces it bit-for-bit and the difference between two redos is the *decision*; `D` turns on rerolling, which calls `WargameEnv.reseed_combat` off the session's own generator so the session still replays from its seed
- **Reproducing a recorded match** (`envs/debug/reproduce.py`, `EpisodeProvenance` in `state/snapshot.py`, `just debug-recording`): a recording carried the full state of every step and **none of the inputs that produced it**, so replay was a video and `just debug` could not open the game you had just watched go wrong. The log **header** now carries the config, the generator state, the combat seed and a `driver` label, and `debug-recording` boots a live env that reproduces the episode bit-for-bit — verified over VP, per-step reward, both sides' positions and wounds. Three load-bearing choices. **A generator state, not a seed**: a training rollout resets without one, so its layout is a point in a continuing stream that no integer names; `np_random.bit_generator.state`, captured before `reset` draws anything, names any point (`seed` rides beside it for humans and is None exactly when the caller passed none). **The config travels with the recording** rather than a path to it, because a path can be edited between recording a match and wanting it back, and a drifted scenario reproduces something that merely looks like it. **It lives in the header, not the snapshot** — a snapshot is a value object compared for equality (`test_v9_milestone_validation` pins replayed == live), and a field on the recorded copy that a live one lacks breaks that; every other episode-static field (`terrain_footprints`, `skip_phases`) is on *both* sides, which is why they do not. `build_env` deliberately does **not** reset — `run_session` owns the reset, and resetting in both places would draw from the stream twice and land on a different layout. `simulate.py` gained `--seed` because it never seeded at all, so its recordings were unreproducible by construction; training recordings need no seed, since each episode's state is captured on its own. **`--from-recording` follows the recording's own actions by default**, which is the only way a *training* recording is steppable: the network that played it was mid-training and was never saved, so no driver reproduces its decisions (`driver` is None on those). Following stops the moment an order is authored — an action recorded for a state you have since altered is a coincidence, not that match — and resumes on rewinding past the divergence; the lookup is by `env.current_turn`, which the rewind restores, so it costs no bookkeeping. **Fidelity, measured:** two rebuilds from one provenance are bit-identical, and replaying a `simulate` recording's actions matched its snapshots exactly over 20 steps; against a *training* recording it is exact at 38 of 40 steps with a transient ~9e-13 on one model at two of them. Both rebuilds agree with each other there, so the difference is between the training process and any reproduction — unexplained, and the reason not to quote that path as bit-identical

## Design

- **The board is continuous.** Locations are real points, built through `position()` / `zero_position()` from `domain/value_objects.py` — never a literal dtype. `POSITION_DTYPE` is the single declaration, which is what made the move off the grid one edit rather than a hunt; a missed site would truncate silently with no exception and no failing test. **Arithmetic widens too** — anything added to or clipped against a position must carry `POSITION_DTYPE`
- **A model has a base, and it is on by default.** `base_radius` (config, inches) defaults to the rules' **32mm infantry base** — radius 0.63" — resolves through `RulesQuantities` and is stored on `WargameModel`. **0.0 is not a neutral setting: it switches off three mechanics at once.** The three cover rays coincide so cover cannot occur at all, models do not collide, and range is centre to centre. That was the default until 2026-08-12, which is why the 25v25 shooting config — which never set it — was the pre-geometry scenario running on the post-geometry engine. Two consequences of turning it on: occupancy can no longer saturate (eight 32mm bases do not fit on a radius-1 disc), and any baseline steering every model at an objective's *centroid* now jams on its own models. It is read off the model rather than passed to `compute_distances`, because there are 17 call sites and a forgotten argument would silently score one of them under dimensionless rules. It shortens the objective distance (`norms_offset`), separates models at placement, insets the board clamp, and widens engagement to base-to-base. Radius 0.0 is the default and reproduces the point-model behaviour every pre-continuous result was measured under
- **Coherency is measured, not enforced — except at deployment.** `domain/coherency.py` is the predicate for `docs/rules/03-moving.md` § Coherency: the 2" chain, the 9" spread, **and** the single-connected-group clause, which the first two do not imply — two pairs 5" apart satisfy both stated conditions and are still not one unit. Base to base like engagement, alive models only, so a casualty never reads as a violation. It decides nothing; the same definition serves the metric (`just measure-coherency`) and will serve any enforcement without copies drifting. The one consequence wired up is `coherency.enforce_at_deployment` (§ Setting up), **off by default**: default placement anchors each model on one *random* squadmate, which bounds the nearest neighbour and leaves unit span unbounded, so deployment is coherent in **0 of 20** episodes and even a policy that never moves scores 0.006. Turning it on is a scenario change that voids the baselines on that config — measured, it *pays*: the bar goes +38.0 → **+58.9**, and every squad-manoeuvring policy gains ~21 vp because a squad that starts concentrated concentrates its fire (`alive` 0.450 → 0.592). **`coherency.enforce_move` is the rule's primary consequence** — a move ending a unit out of coherency is undone (`revert_unit`, the spec), or the models in breach are (`revert_model`), and there is no third mode — a `clamp` that shortened the move along its own segment was **removed on 2026-08-16** once all three measured the same ~26 vp cost, and it could never shorten a pure-spread breach anyway, silently degrading to a full revert. **Warm-start required**: turning any of them on and training from scratch collapses the run (−75.3 with `revert_unit`, against a from-scratch control at +90 by epoch 40). The revert *taxes* the bar, and `revert_unit` **freezes** policies that break formation by design (`split_evenly` −41 → −98, `alive` 0.10 → 0.96 — every move cancelled, which is this repo's worst failure mode); the same cliff caught a *trained* policy, which scored −75.3 vp_margin against its bar's +42.7 with `on_obj` 0.08 and `alive` 0.63 — it learned not to move. The spread condition is collective, so the modes coincide once any model exceeds the cap. **The revert cascades**: putting a model back on ground another legally took is a *second* illegal state, checked by the same rule, so the displaced model reverts too. **Selection and the cascade both iterate, and they alternate** — reverting a model changes whether its unit is coherent, and the cascade's own additions can break *their* units. A single pass left `revert_model` breaking units at the same rate as no enforcement at all (0.024 v 0.025, against `revert_unit`'s 0.000); iterating both to a fixed point took it to 0.000. What a revert cannot do is *repair*: a unit already split by casualties is incoherent before it moves, so enforcement stops at the starting configuration and attrition closes the rest. **`coherency.attrition`** is the last rung (§ Regaining coherency), at the final phase boundary of a player's turn — there is no End of Turn phase and adding one would change episode length. Casualties get **no kill credit**, per the rule that they trigger nothing firing on destruction. **Read its cost in vp, not in bodies**: it is 50.7% of all losses and still *recovers* ~10 of the 17 vp the move rule took, because it culls stragglers and the survivors are better concentrated (`on_obj` 0.645 → 0.918 while `alive` falls) **`eval/coherency_rate` and `eval/models_out_of_coherency` are the readout** (`env_components/coherency_tracker.py`), sampled once per *movement* phase and logged with no config flag -- a run training under the rule with no record of whether it held formation is the situation they exist to prevent. Read them together: the rate is confounded with squad size, since a unit shot down to one model is coherent by definition and the rate therefore climbs as an army dies. **`observe_coherency` is the other half**: it puts the spread ratio and the component fraction on each model's token, because the rule's other two clauses had no input — the 9" spread is a *furthest*-neighbour quantity and the existing column is a nearest one, and connectivity is a transitive closure. Add the inputs before pricing or enforcing anything that keys on them. **`observe_unit_centroid` is the direction half**: both of those are *magnitudes*, and the spread ratio reads identically from either end of a strung-out unit, so a model could be told its unit was coming apart with nothing to act on. It adds the vector to the unit's live centroid (two columns, over the spread cap, clipped per axis so the sign survives at any distance) — the quantity `ScriptedSquadMarchPolicy` actually steers every member of a unit along, which is why scripted formation holds by construction. Measured on one behaviour clone it takes unit coherency **0.665 → 0.793** with `vp_margin` unchanged, and the fragmentation signature collapses (`spread fail` 0.151 → 0.018 against the demonstrator's 0.002). - **A footprint is a continuous rectangle, and configs author cells.** `Footprint.from_cell_rect` is the single boundary that converts: `(5,5,5,5)` names one cell and becomes `[5,6]x[5,6]`. Read literally as a continuous rect it would have zero area. The same off-by-one lurks in mirroring — reflect about `width`, not `width - 1`. Nothing fails when you get this wrong; the terrain just quietly gets smaller
- Pre-compute expensive ops at `__init__` (numpy vectorized)
- **Rules distances are authored in inches; coordinates are in units.** `inches_per_unit` (default 1.0) is the mapping, `domain/scale.py` owns the conversion, and `resolve_rules_quantities(config)` resolves every rules distance into units **once at construction** — read them off `BattleView.rules_quantities`, never divide at runtime. `domain/rules_constants.py` holds the *rules'* values (mirrored from `docs/rules/constants.yaml`, pinned by a test); where the env deliberately differs, the config states it and `docs/rules/implementation-status.md` records it. Do not "fix" a divergence by wiring in a rules constant — every shipped baseline was measured under the env's value
- **`RulesQuantities` holds only what is read through it.** Add a field with the code that consumes it, never ahead of it: a config field that is settable but inert is the same failure this project hit with reward levers the agent could not observe
