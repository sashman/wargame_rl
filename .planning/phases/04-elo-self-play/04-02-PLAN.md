# Elo-Based Self-Play, Wave 2 — The Schedule, the Arena and the Ledger

**Goal:** A rating table over the nine scripted baselines, with the deployment-zone and
first-turn advantages in Elo points and bootstrap intervals. **This wave changes
nothing under `envs/` or `model/`.**

**Architecture:** A leg is a config transform, not new env code — both imbalance axes
are already config fields, and `scripted_baseline` already seats a player-side baseline
on the opponent side. The arena **wraps** `evaluate_selector` through
`set_opponent_policy`; opponent identity is state on the env, not a parameter of the
scoring loop. The ledger stores raw per-layout legs and fits on read.

**Spec:** [docs/elo.md](../../../docs/elo.md) § The match schedule, § Provenance.
Context and decisions: [04-CONTEXT.md](04-CONTEXT.md) D-07 to D-16.

## Global Constraints

- Every function typed; `from __future__ import annotations`. Mypy strict.
- **`wargame_rl/wargame/envs/baseline/evaluate.py` must not be modified.** If it seems
  to need a change, the design is wrong — re-read D-07.
- `rating/arena.py` is the only module in `rating/` that may import `WargameEnv`.
- Scripts are raw `sys.argv`, not Typer. Optional args arrive as **empty strings**.
- `just format && just lint` before any commit; both golden tests bit-identical.

### Task 1: Entrants and the schedule

**Files:**
- Create: `wargame_rl/wargame/rating/entrant.py`, `wargame_rl/wargame/rating/schedule.py`
- Test: `tests/test_rating_schedule.py` (create)

**Interfaces:**

```python
# entrant.py
@dataclass(frozen=True, slots=True)
class Entrant:
    name: str
    build: Callable[[WargameEnv], ActionSelector]
    shoots: bool
    kind: Literal["baseline", "checkpoint"]
    source: str | None = None
    parent: str | None = None  # lineage, for the Phase 05 pool manifest
```

`build` is a factory rather than a selector because a network entrant must be sized
from the leg's env; a scripted factory ignores its argument.

```python
# schedule.py
ELO_SEED_BASE: int = 900_000


class Zone(str, Enum):
    zone_1 = "zone_1"
    zone_2 = "zone_2"


class Seat(str, Enum):
    a = "a"
    b = "b"


@dataclass(frozen=True, slots=True)
class Leg:
    a_zone: Zone
    first_mover: Seat

    @property
    def sigma_zone(self) -> float: ...  # +1 zone_1, -1 zone_2
    @property
    def sigma_turn(self) -> float: ...  # +1 A first, -1 B first


FOUR_LEGS: tuple[Leg, Leg, Leg, Leg]


def config_for_leg(base: WargameEnvConfig, leg: Leg) -> WargameEnvConfig: ...
def layout_seeds(n_layouts: int, seed_base: int = ELO_SEED_BASE) -> list[int]: ...
def combat_seeds_for(layout_seeds: Sequence[int]) -> list[int]: ...
def pairings(entrants: Sequence[str]) -> list[tuple[str, str]]: ...
```

`Leg` carries no entrants and no seeds — those come from the pairing loop and the seed
space. Bundling them would force one object per layout, which is the wrong granularity
for the same reason `play_match(..., layout_seed)` is.

The schedule is balanced in both axes by construction, so the ratings are unbiased even
before the `h` terms are fitted — and *because* both axes vary independently, both
terms are identified. Swapping zone and turn together would confound them into one
number from which neither is recoverable (pinned by a test in wave 1).

- [ ] **Step 1: Write the failing tests**

- `test_all_four_leg_configs_fingerprint_identically` — deferred to Task 3, but write
  the leg-construction half now.
- `test_config_for_leg_refuses_default_zones` — `battle_factory.py:185` derives
  `(0,0,W//3,H)` / `(W*2//3,0,W,H)` when a config leaves the zones `None`, so swapping
  two `None`s is a **silent no-op**: the zone leg would be inert and `h_zone` would fit
  noise and report it as a number. Raise instead.
  (`configs/golden/25v25_shooting_opponent.yaml:169-170` sets both explicitly.)
- `test_config_for_leg_refuses_fixed_positions` — `has_fixed_model_positions` /
  `has_fixed_opponent_positions` make the swap inert the same way.
- `test_the_four_legs_share_terrain_and_objectives` — reset each leg's env at the same
  layout seed; terrain footprints and objective locations must be identical, and only
  deployment differs. **This is also the guard for the `turn_order` RNG hazard:**
  `_resolve_player_side` (`wargame.py:1022`) draws at `:1029` and runs at `:781`,
  *before* the map-pool draw, and only under `turn_order: random`. Both fixed values
  draw nothing, so the four legs agree with each other — but a config whose own
  `turn_order` is `random` is on a *different* layout stream from its
  `measure-baselines` numbers. Assert the agreement; document the difference.

- [ ] **Step 2: Implement**

`config_for_leg` returns a **new** config via `model_copy(update=...)`, revalidated
(unlike `_MirroredEnv`, whose swap would be rejected by the model-list pairing
validator — here nothing invalid is produced). Never mutate a live env's config:
`turn_order` happens to be read only at reset, but `_skip_phases`, `max_turns` and both
`ActionHandler`s are cached at `__init__`.

### Task 2: The arena

**Files:**

**Interfaces:**

```python
@dataclass(frozen=True, slots=True)
class LegResult:
    entrant_a: str
    entrant_b: str
    leg: Leg
    layout_seeds: tuple[int, ...]
    combat_seeds: tuple[int, ...]
    margins: tuple[float, ...]  # a_vp - b_vp, per layout, seed order
    wins: tuple[float, ...]
    objectives_held: tuple[float, ...]
    coherency_rate: float | None


def play_leg(
    entrant_a: Entrant,
    entrant_b: Entrant,
    base_config: WargameEnvConfig,
    leg: Leg,
    layout_seeds: Sequence[int],
    combat_seeds: Sequence[int],
) -> LegResult: ...


def play_pairing(
    entrant_a: Entrant,
    entrant_b: Entrant,
    base_config: WargameEnvConfig,
    n_layouts: int,
    seed_base: int = ELO_SEED_BASE,
) -> list[LegResult]: ...  # exactly four, one per Leg
```

The body is deliberately thin:

```python
env = create_environment(env_config=config_for_leg(base_config, leg))
env.set_opponent_policy(
    SelectorOpponentPolicy(env, select=entrant_b.build(env), label=entrant_b.name)
)
result = evaluate_selector(
    entrant_a.build(env),
    env,
    list(layout_seeds),
    name=entrant_a.name,
    combat_seeds=list(combat_seeds),
)
```

**Wave-2 note:** `SelectorOpponentPolicy` lands in wave 3. Until then, seat entrant B
by naming `scripted_baseline` in the leg config's `opponent_policy` — which is all the
scripted ladder needs, and is why this wave changes nothing under `envs/`.

`evaluate_selector` reusing one env across all seeds is **the requirement, not an
obstacle**: it is what lets a network entrant load its checkpoint once per leg rather
than once per layout. `reset()` never touches `_opponent_policy`, so an arena-seated
opponent persists.

Carry `coherency_rate` onto `LegResult` — CLAUDE.md's standing rule is that a
`vp_margin` without a coherency column is a result plus an unstated claim that the
moves earning it were legal.

- [ ] **Step 1: Write the failing tests**

  different measurements, which would silently break the ΔElo ↔ `vp_margin`
  cross-check.
- `test_play_pairing_returns_one_result_per_leg` — exactly four, each with a distinct
  `(sigma_zone, sigma_turn)`.
- Use `configs/dev/tiny.yaml` (or a local `_make_env`-style helper) so the test is

### Task 3: The ledger

**Files:**
- Create: `wargame_rl/wargame/rating/ledger.py`
- Modify: `.gitignore`, `.claude/hooks/docs_check.py`
- Test: `tests/test_rating_ledger.py` (create)

**Interfaces:**

```python
LEDGER_ROOT: Path = Path("ratings")


class RatingScenarioMismatch(ValueError): ...


def canonical_scenario(config: WargameEnvConfig) -> dict[str, Any]: ...
def fingerprint(config: WargameEnvConfig) -> str: ...  # sha256, first 16 hex


class LedgerEntrant(BaseModel): ...  # name, kind, source, parent, decode_topk


class LegRecord(BaseModel):
    ...  # entrants, leg axes, seeds, margins, wins,
    #   objectives_held, code_revision, recorded_at


class Ledger(BaseModel):
    ...  # fingerprint, scenario, margin_scale,
    #   entrants, legs


def path_for(fingerprint: str, root: Path = LEDGER_ROOT) -> Path: ...
def load(fingerprint: str, root: Path = LEDGER_ROOT) -> Ledger | None: ...
def append(
    legs: Sequence[LegResult],
    config: WargameEnvConfig,
    entrants: Sequence[Entrant],
    root: Path = LEDGER_ROOT,
) -> Ledger: ...
def leg_results(ledger: Ledger) -> list[LegResult]: ...
```

**The fingerprint is over the *scenario*.** Input is `config.model_dump(mode="json")` —
the same dump `EpisodeProvenance` already uses (`wargame.py:311`), so there is one
serialisation of a config in the repo.

**Dropped:** `render_mode`, `config_name` (presentation); `opponent_policy` (**this is
entrant B**); `turn_order` (**this is the leg axis**); `track_exposure` (instrumentation
that changes no outcome); `reward_phases` (affects training, not an argmax playout).

**Canonicalised:** `deployment_zone` / `opponent_deployment_zone` →
`sorted([...])` under one `zone_pair` key; the two `(count, models)` pairs → `sorted`
under one `army_pair` key. This is what makes the zone swap fingerprint-invariant.

Everything else — board, terrain mode, `map_pool.names`, `mission`, `skip_phases`,
`n_rounds`, `base_radius`, `coherency.*`, `objective_*`, every `observe_*` flag, the
budgets — is **in**. Rule of thumb: *if it changes what happens on the board, it is in
the fingerprint.*

`docs/elo.md` says only "excluding rendering and logging fields". Taken literally that
puts the four legs of one table into four different ledgers, because the schedule
deliberately varies two of the excluded-here fields. **This is the correction that
makes the feature work at all.**

- [ ] **Step 1: Write the failing tests**

- `test_all_four_leg_configs_fingerprint_identically` — the single assertion that
  proves the canonicalisation, and the one that fails loudly the day someone adds a
  config field to the leg transform.
- `test_the_ledger_refuses_a_second_fingerprint` — `RatingScenarioMismatch`, raised not
  warned. CLAUDE.md records what happens to warnings (TF32, `last.ckpt`).
- `test_a_changed_board_changes_the_fingerprint` — the deny-list must not be so eager
  that it stops noticing real scenario changes.
- `test_the_ledger_round_trips` — `append` then `load` then `leg_results` reproduces
  the `LegResult`s.

- [ ] **Step 2: Implement**

Store **raw per-layout legs, not fitted ratings**: the bootstrap resamples layouts and
needs them, adding one entrant would otherwise mean replaying every pairing, and
recalibrating `s_m` would mean replaying everything. `just elo-table` fits on read.

Record `code_revision` (`git rev-parse --short HEAD`, tolerating a non-repo) and
`decode_topk` per entrant. A rating is only comparable at a fixed decode.

- [ ] **Step 3: Make `ratings/` a committed artefact**

Unlike `checkpoints/` and `recordings/`, the ledger is a durable measurement in the
class of `reports/`. Do **not** add it to `.gitignore`; **do** add it to the
`reports/`/`.planning/` exemption list in `.claude/hooks/docs_check.py`, since it
records what was measured at the time.

### Task 4: `measure-elo`, `elo-table`, and the seat-parity gate

**Files:**
- Create: `wargame_rl/wargame/rating/table.py`, `scripts/measure_elo.py`,
  `scripts/elo_table.py`
- Modify: `Justfile`

**Recipes** — note `just` requires the variadic parameter last:

```just
measure-elo env_config n_layouts='100' +entrants='random squad_march squad_march_shoot'
elo-table   env_config
```

- [ ] **Step 1: Implement the scripts**

Raw `sys.argv`, module docstring as help, guarding optional args with
`if len(sys.argv) > N and sys.argv[N]`. Entrants are named the way every other tool
here names them — a baseline registry key or a path to a `.ckpt` — through
`build_action_selector` from wave 1, so a scripted policy and a checkpoint are entered
identically.

Print the table with `coherent` and `adrift` columns and **quote the interval, not the
point**. A rating without its bootstrap interval is the same failure as a
`success_rate` with no floor and no bar.

Put the `turn_order: random` hazard in the recipe's comment block: on a config whose
own `turn_order` is `random`, a rated leg is on a different layout stream from that
config's `measure-baselines` numbers.

- [ ] **Step 2: The seat-parity gate**

```bash
just measure-elo configs/golden/25v25_shooting_opponent.yaml 30 squad_march_shoot squad_march_shoot
```

`squad_march_shoot` against itself over the balanced four legs must score an aggregate
margin of **≈ 0**. The reward, coherency and exposure trackers are player-side only and
`terminate_on_player_elimination` is player-only; those are measurement-only or
default-off, so the game *should* be seat-symmetric — but that is a claim, not a fact.

**A non-zero result is a bug found and it blocks the phase.** Record the number either
way.

- [ ] **Step 3: The first real table**

```bash
just measure-elo configs/golden/25v25_shooting_opponent.yaml 100 random greedy_nearest \
    split_evenly squad_march contest_and_spread squad_march_shoot squad_march_deny squad_march_take
just elo-table configs/golden/25v25_shooting_opponent.yaml
```

Cross-check the ordering against the `vp_margin` table already recorded in that
config's own header, and the magnitudes against `ΔR ≈ 173.7 · m̄ / s_m`. If they
disagree badly, one of them is measuring a different scenario — most likely the
`turn_order` layout-stream difference above.

- [ ] **Step 4: Commit**

```bash
just validate
git commit -m "feat: scripted baselines get a rating, and the zone advantage gets a number"
```
