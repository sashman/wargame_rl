# Elo-Based Self-Play, Wave 4 — A Trustworthy `p`, Then a Pool That Uses It

**Goal:** Make the rating table sound enough that a *probability* read off it can
steer training, then build the snapshot pool and the PFSP sampler that read it.

**Why in that order.** PFSP samples an opponent with probability a function of
`p = P(learner beats snapshot)`, and `p` comes from the rating table (D-01: self-play
reads the table rather than maintaining a second win-rate estimate). Two known defects
sit between the table and a trustworthy `p`, both surfaced after wave 3 shipped, both
recorded in [docs/elo.md](../../../docs/elo.md) § Open gaps:

1. **The engine seat is an unbalanced axis.** Entrant A always takes the player seat
   and `pairings()` lists each pair once *in input order*, so the first-named entrant
   sits on the player seat in every pairing and the last-named never does. On
   `configs/golden/25v25_shooting_opponent.yaml` the seats differ by **−24.6 ± 9.4 vp**,
   which makes ratings there a function of argument order.
2. **An entrant seated only as B has no coherency figure**, because `evaluate_selector`
   measures the player seat. That is a live violation of the repo rule that no score is
   quoted without coherency, and it is the same asymmetry seen from the metrics side.

Feeding self-play a `p` carrying either defect would spend GPU on it.

**Spec:** [docs/elo.md](../../../docs/elo.md) — corrections 1–5 and § Open gaps.
Context and decisions: [04-CONTEXT.md](04-CONTEXT.md).

### Task 1: The seat becomes a fitted term, not an assumption

**Files:**
- Modify: `wargame_rl/wargame/rating/elo.py`, `wargame_rl/wargame/rating/table.py`,
  `wargame_rl/wargame/rating/schedule.py`
- Create: `tests/test_rating_seat_term.py`

Extend the model with a third advantage term, on the same footing as the two that
already exist:

```
E[s] = 1 / (1 + 10^(−(R_A − R_B + σz·h_zone + σt·h_turn + h_seat) / 400))
```

`σ_seat` is **+1 on every row**, because A always occupies the player seat. That looks
unidentifiable and is not: identification comes from the **cycle structure of the
pairing graph**. A constant column lies in the span of the `e_A − e_B` columns only if
some rating vector has every pairwise difference equal to 1, which any cycle forbids —
around a triangle the differences sum to zero and the ones do not.

**Verified numerically before this plan was written** (design = all pairs × four legs,
one rating anchored):

| entrants | design | rank | full rank? | cond | `se(h_seat) / se(h_turn)` |
|---|---|---|---|---|---|
| 2 | (4, 4)  | 3 | **no**  | —    | — |
| 3 | (12, 5) | 5 | yes | 6.98 | 3.00 |
| 4 | (24, 6) | 6 | yes | 6.58 | 2.45 |
| 6 | (60, 7) | 7 | yes | 7.36 | 2.12 |
| 9 | (144, 8)| 8 | yes | 9.17 | 1.96 |

Three consequences, all of which must land in code:

- **Refuse at fewer than three entrants**, in the same class as the existing refusal of
  a schedule that moves the two axes together. `fit_ratings` already refuses a
  confounded design; this is the same failure with a different cause, and the message
  should say so.
- **`h_seat` is the weakest term in the fit** — its standard error is 2–3× `h_turn`'s,
  because it is identified only indirectly. Print it with its interval like the others,
  and say in the table's footer that it is the least-determined column.
- ⚠ **This does NOT replace `just measure-seat-parity`.** The direct measurement puts
  one policy on both seats and is a far higher-powered estimator of the same quantity;
  the fitted term absorbs the confound so ratings stop depending on argument order.
  Keep the gate, and cross-check the two — a large disagreement means the constant-in-Elo
  assumption is wrong, which is live given `h_turn` was measured to **change sign with
  shooting**.

The alternative — playing every pairing in both A/B orders — **doubles the legs for the
same information** and is rejected on that ground. Update `pairings()`' docstring, which
currently carries the caveat rather than the resolution.

**Verify:** rank and conditioning reproduced as a test over 2–9 entrants; a synthetic
corpus generated with a known `h_seat` is recovered to within its interval; a two-entrant
table raises; ratings fitted on a corpus with a real seat advantage are **invariant to
the order entrants are named in**, which is the defect this closes.

**intended** coherency: the player path reads it off
`ActionHandler.intended_coherency_last_move`, and the opponent path never records it.

figures agree within noise; an entrant named last in `measure-elo` comes back with a

existing tests, since nothing on that path moves.

### Task 4: The snapshot pool

**Files:**
- Create: `wargame_rl/wargame/rating/pool.py`,
  `wargame_rl/wargame/model/common/snapshot_callback.py`, `tests/test_rating_pool.py`
- Modify: `wargame_rl/wargame/rating/ledger.py`

`SnapshotPool` is a fixed-capacity, ordered collection of frozen opponents — a snapshot
path, the epoch it was taken at, and its rating if one has been fitted. Numpy and
dataclasses only.

- **Snapshot every `snapshot_every_n_epochs`.** A Lightning callback, modelled on
  `PeriodicLastCheckpoint` (`model/common/checkpoint_callback.py:19`), which already owns the "write every N epochs *and* at
  `on_train_end`" behaviour. ⚠ `SIGKILL` triggers neither, and SIGKILL is the prescribed
  way to stop these trainers — so a pool is routinely up to N epochs stale, exactly as
  `last.ckpt` is. Say so where it is read.
- **Entry zero is an anchor that is never evicted** — the initial policy, or a named
  scripted baseline. Without it a pool can drift as a whole and lose its floor, and
  `random` is what the rating scale is anchored to.
- **Eviction thins uniformly rather than dropping the oldest**, so the pool always spans
  the whole run rather than its recent past. Keeping only recent snapshots is how
  self-play forgets how to beat what it already beat.
- **Disk is a real constraint here.** Checkpoints are deliberately not uploaded to Wandb
  because each run pushed ~591 MB and filled the quota; a pool multiplies the local
  footprint by its capacity. Default the capacity low and state the megabytes per
  snapshot in the config field's help.

The ledger gains a **`decode_topk` per row** and refuses a table that mixes decodes, in
the same class as its existing refusal to mix scenarios. Self-play games are sampled
rather than argmax-decoded, so they must not silently join an argmax-decoded evaluation
ledger.

**Verify:** thinning keeps the anchor and spans the run; a pool round-trips through disk;
capacity is honoured; `decode_topk` mixing raises.

### Task 5: PFSP sampling, and the wiring that is a no-op when off

**Files:**
- Create: `wargame_rl/wargame/rating/pfsp.py`, `tests/test_pfsp.py`,
  `tests/test_self_play_wiring.py`
- Modify: `wargame_rl/wargame/envs/types/config/env.py`,
  `wargame_rl/wargame/model/ppo/lightning.py`, `docs/self-play.md`

`pfsp_weights(p, mode, uniform_floor)` — numpy only, no project imports:

| mode | weight | picks |
|---|---|---|
| `hard` | `(1 − p)²` | opponents the learner loses to |
| `even` | `p(1 − p)` | opponents it is level with |
| `uniform` | `1` | the control |

Mixed with a uniform floor so no snapshot is starved, and normalised. `p` comes from the
rating table via the Elo expectation, **not** from a second win-rate estimate.

**Wiring.** `_ensure_rollout_envs` (`model/ppo/lightning.py:604`) builds and caches the
rollout envs; `set_opponent_policy` (`envs/wargame.py:334`) already exists and `reset()` never touches
`_opponent_policy`, so a sampled opponent persists until it is replaced.

Config, every field defaulting to the no-op:

```yaml
self_play:
  enabled: false              # off => nothing below is read, and no RNG is drawn
  snapshot_every_n_epochs: 25
  pool_capacity: 8
  anchor: squad_march_take    # entry zero, never evicted
  sampling: hard              # hard | even | uniform
  uniform_floor: 0.1
  decode_topk: 1              # the opponent's decode, recorded per rated row
```

Three properties this must have, each a test:

- **Off is bit-identical.** A run with `enabled: false` matches a run on a config with no
  `self_play` block at all, tensor for tensor — the `augment_start` standard.
- **The sampler has its own stream.** Seeded off the training seed but drawn separately,
  so turning self-play on does not shift the layout or dice streams and the two arms stay
  comparable. This is the same failure mode as `turn_order: random` consuming a layout
  draw, which is already documented and pinned.
- **Sampling is reproducible.** Training is deterministic given seed + config + code, and
  an opponent schedule that varies run to run would end that.

⚠ **The learner only ever trains the player seat.** `learner_side` is Phase 05, so a
snapshot seated as the opponent is playing a seat it never trained on. On a scenario that
fails seat parity that is not a fair mirror, and `h_seat` from Task 1 is what says how
unfair. **Do not start a self-play run on a config whose seat-parity gate fails** — this
is the phase's own blocking precondition, and it is why Task 1 comes first.

`docs/self-play.md` is written here, for the same reason `docs/elo.md` was: it is cited
throughout this phase as a canonical reference and has never existed. Write it against
what ships, not against what was planned.
