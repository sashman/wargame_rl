# The Opponent Turn — Wave 1: Instrument, then batch the squad's geometry

Read [05-CONTEXT.md](05-CONTEXT.md) first. It carries the profile every number
here refers to, the ceiling on what this phase can win (**~12–15% of epoch
wall-clock, not 2×**), and one target already measured and rejected.

## Global constraints

**The gate is bit-identity, and it is not negotiable.** `test_reward_golden`
pins reward, VP and every model position with `assert_array_equal` and is
verified sensitive to one ULP. The opponent moves models, so it is inside that
gate. A change that cannot hold it **does not ship** — the corpus of measured
results is worth more than any millisecond here.

⚠ **Run the gate. Never argue that a change must be safe.** Batching a per-point
boolean is safe in principle; numpy may still take a different code path for a
batched call than a scalar one. The only evidence that counts is the test.

⚠ **Do not regenerate a golden in this phase.** `--regenerate` exists for when
the reward *should* change. Nothing here should change it. A red golden means the
optimisation is wrong, not that the fixture is stale.

⚠ **Do not touch `ActionHandler.apply`'s movement solver in this wave** (target 4
in the context). Two attempts at that solver were measured and reverted, and
CLAUDE.md says not to attempt a fourth.

## Task 1: Put the breakdown in the tool

The context's profile came from a scratch script. Land it, so the before/after is
reproducible and the next person cannot repeat the double-counting mistake.

Extend `scripts/measure_throughput.py` to break the existing `opponent turn` line
into:

```
opponent turn                    3.755 ms   42.9%
  opponent action mask           0.612 ms   16.2%
  policy.select_action           1.205 ms   31.9%
    select_movement              1.057 ms
      step_toward_objective      0.748 ms
      squad_objectives           0.141 ms
  action_handler.apply (move)    0.902 ms   23.9%
  resolve_shooting               0.777 ms   20.6%
  [unaccounted]                  0.275 ms    7.3%
```

Two requirements that are the whole point of the task:

- ⚠ **`_resolve_shooting_action` is shared with the player's turn.** Attribute it
  with a re-entrancy flag set inside `_apply_opponent_action`. Wrapping it
  naively double-counts and makes the sections sum to a tidy, wrong 100% — which
  is exactly what happened on the first pass.
- **Print the unaccounted remainder.** A breakdown that does not show its own
  residual cannot be checked, and this one is 7.3%.

The sub-rows are nested one level under their parent, so a reader can see that
`select_movement` is inside `select_action` rather than beside it.

Keep the existing top-level output unchanged, so every figure quoted from this
tool before today still reads the same way.

## Task 2: Batch the squad's arrival geometry

`step_toward_objective` is **70.8% of `select_movement`** — 14.7 calls per
movement phase at ~101 µs each, every one doing `area.contains(x, y)` and
`area.distance_to_point(x, y)` as **scalar** queries against a ruin outline.

Every member of a squad is tested against **the same objective**. The repo
already has vectorised polygon primitives (`polygons_contain_points`).

So: compute the squad's arrival geometry **once per squad**, over all its
members' positions in one call, and have the per-model branch read the result
rather than recompute it.

Constraints on the shape:

- The **decision** must be unchanged for every model. This is a caching and
  batching change, not a rule change: the same action index for the same board.
- ⚠ The per-model `contains` test and the per-model `distance_to_point` must
  produce **bit-identical** floats to the scalar path. Each point is independent,
  so the arithmetic per point should be unchanged — but batching is exactly where
  numpy may reduce differently. If a batched distance cannot be made
  bit-identical, batch only the boolean `contains` test and leave the distance
  scalar. **Half the win with the gate held beats the whole win without it.**
- `step_toward_objective` is a module-level function in
  `envs/baseline/policy.py` used by more than one policy. Either keep its
  signature and add a batched sibling, or move the batching into
  `select_movement`. Do not change the behaviour of any other caller.

## Task 3: The regression test the fix needs

`tests/test_baseline_geometry.py`: the batched squad geometry equals the
per-model loop **exactly**, over a sweep of seeds and both an area objective and
a marker objective.

⚠ **Assert with `assert_array_equal`, not `allclose`** — the whole risk of this
change is a last-bit difference, and a tolerance would wave through precisely the
regression this test exists to catch. Verify the test is sensitive: perturb one
coordinate by one ULP and confirm it fails.

Include the case the context's rejected target teaches: a squad whose members
share `dx`, `dy` and `max_step_length` and differ only in `model_idx`. That is
the common case, and a batching bug that collapses per-model state would pass any
test built only from a one-model squad.

## Task 4: Prove the scripted bar did not move

The gate tests are necessary and not sufficient — they cover three configs and a
recorded match, not the map pool.

```
just measure-baselines configs/golden/25v25_maps_two_mode.yaml 100 "" 700000
```

before and after. **`squad_march_take` must score identically to every printed
digit** — `vp_margin`, `held`, `alive`, `coherent`. This is the same cross-config
bridge the advance re-encoding used, and it is the check that catches a change
the goldens' three configs happen not to exercise.

Record both outputs in the summary. A difference of any size in any column means
stop and diagnose, not "close enough".

## Task 5: Record what it bought

Re-run `just measure-throughput` on the same config and record before/after for
the opponent turn and for `env.step` as a whole.

⚠ **Quote the epoch-level number, not just the env-step one.** The env step is
~19.2 s of a ~30 s CPU epoch, so a 20% cut to `env.step` is ~12% of the epoch.
Reporting only the local speedup overstates it by roughly 2×, and this repo's own
history is full of local wins quoted as global ones.

⚠ **State the hardware and that it is CPU.** These numbers came from a Ryzen
3950X with no usable GPU; the balance between the environment and the update is
different on a machine where the update is actually on a card.

## What is NOT in this wave

  the command phase pays for a mask it does not need, or it may be irreducible.
- The `resolve_shooting` asymmetry (target 3) — **explain it before optimising
  it**, and it is likely a workload artefact of profiling against random play
  rather than a defect. If it turns out to be a defect it belongs in its own PR,
  because a defect there changes behaviour and this wave must not.
- `ActionHandler.apply`'s movement solver (target 4).
- `best_action_toward` — measured at 2.1% and **rejected**; see the context.
